01 · 核心矛盾

模型只会生成 Token，但 Agent 要完成任务

只看聊天界面，很容易产生错觉：模型越来越强，再接几个工具，就是好用的 Agent。真相是——模型能"说"，却不能"做"。它说出"我要读 config 文件"之后，什么都不会发生，除非有一层东西替它真的去读。

Model · 大脑思考、拆解、决定调哪个工具
（碰不到外部世界）
请求 / 上下文→←结果喂回
Harness · 挽具组织与约束
不思考、不判断
工具 / 执行→←结果回传
外部世界 · 四肢代码 / Shell / Web
真正对外做功

Agent 系统 = 整个人：大脑再聪明，神经断了，四肢也动不了。

试试这个开关：同一句话，有没有 Harness

模型输出："我要读取 config 文件，检查数据库配置。"
一句话记忆：核心问题不只是"如何让模型更好地思考"，还有"如何让输出变成可执行、可验证、可纠错的行动"。
02 · 公式与 10 问

Agent = Model + Tools 只适合最小原型

进入真实项目，Agent 系统还要处理上下文、状态、权限、持久化和可观测性。书里给出下面这组要素（作者声明：不必当成严格公式），Harness 负责组织这些部分。

Agent System = Model+ Context+ Tools+ State+ Loop+ Execution Environment+ Policy+ Persistence+ Observability

10 个问题 ↔ 公式要素（把鼠标放上去 / 点一下）

  • Q1能看到什么上下文？
  • Q2能调用哪些工具？
  • Q3工具在哪里执行？
  • Q4哪些操作需要授权？
  • Q5失败后如何继续？
  • Q6历史状态保存在哪里？
  • Q7一轮什么时候结束？
  • Q8能否派生子 Agent？
  • Q9能否运行代码？
  • Q10如何恢复、审计和调试？

发现了吗：10 问不是散问题，是在逐个点名公式里的要素。整本书就是逐章回答这 10 个问题。

一句话记忆：Agent Performance = f ( Model, Harness, Tools, Context, Policy, Environment )。
03 · Harness 是什么

挽具：把"说"的力量，约束并导向外部世界

Harness 原意是马具 / 挽具——套在马身上、把马的力量约束并导向某个方向的装备。模型只会生成 Token（一股原始力量），Harness 把这股力量导向外部世界，让它真正完成任务。

两项职责

  • ① 连接：把模型与外部世界（External World）接起来
  • ② 约束：规定模型能做什么、怎样做、留下什么状态

模型在循环中的位置

感知 → 思考 → 行动 → 观察。模型只占"思考"一格；感知、行动、观察全靠 Harness 替它张罗。

三个容易混淆的概念

只是文字Function Calling

模型输出一段结构化文字，表达"我要调某函数、参数是这些"。仍然只是"说"，没有真的执行。

一种接法MCP

让外部系统连接各种工具/数据源的协议。解决"工具怎么接进来"，只是 Harness 的一个环节，不是全部。

真正干活Harness

真正读懂意图 → 执行 → 回传结果 → 决定下一轮的那个部件。执行 · 回传 · 重试 · 裁剪 · 喊停 · 拦截授权都归它。

一句话记忆：模型出主意，Harness 跑腿。
04 · 为什么 DSH 值得单独写一本书

公开的不是产品，是「组织方式」这个样本

市面上已有大量 Coding Agent、Agent 框架和围绕 MCP 的工具生态。如果 DSH 只是又一个能改代码的 Agent，就不值得写一本书。选它，是因为它公开展示了一种不同的组织方式。

# 全是可组合插件

公开得彻底在哪

Model Adapter、Tool Registry、Session Log、Agent Loop 这些产品能力全部进入插件体系——扩展这些能力，不必先修改特权产品核心。

但 ≠ 没有核心

Cordis 定义了 Plugin / Context / Service / Event / Effect / Lifecycle 的组合语义。核心不管具体活，只管组件如何组合和退出。

保守判断（1.4）：DSH 的研究价值来自公开的模块边界和扩展机制，而不是尚未形成的行业地位——叫"Agent 操作系统"还太早，即使它最终没成为标准，也留下了一套值得借鉴的 Agent Runtime 设计思路。
05 · 产品 vs Runtime

Runtime 是地基，产品是地基上盖的房子

从用户界面看，DSH 是完整产品：选 Workspace、输任务、批准敏感操作、拿结果。从架构看，这只是某一种组件组合的运行结果——DSH 把"一个 Agent 具备哪些能力"变成了装配问题。

产品Runtime
面向用户开发者
是什么有界面、默认配置、开箱即用底层引擎：调度、执行、Loop、插件挂载
比喻房子地基

4 套 Preset = 同一套 Harness 的预设配置

不同会话需求不同：一个会话可能要完整文件系统、Shell、Skills、Plan、Subagent、Workflow、Sandbox、Approval；另一个只要 Bash + 文件编辑器 + 固定 Prompt。传统框架要维护 3 套配置甚至 3 套 Loop，DSH 用 Preset 按会话组合能力。调的是 Harness 配置，不动模型权重。

06 · 一切皆插件

统一的是组织方式，不是职责

第一眼容易误解：既然能力都是插件，是不是想换就换、想删就删？并不是。组件之间有依赖关系——依赖的能力消失，组件就无法运行或被卸载。"Everything is a Plugin"描述的是能力如何参与组合。

职责组织方式
是什么每个插件自己干什么对外暴露接口、被调度 / 拦截 / 控制循环
例子模型适配器连模型、会话系统存状态、智能体循环推推理加载、依赖、作用域、生命周期（运行时统一管理）
是否统一不统一，各管各的被统一到同一套规则下

判断标准

与"具体是谁、干什么"无关的 → 组织方式；绑定的 → 职责。换一个插件：变的是职责，不变的是组织方式。

依赖"能力"，不依赖"实现"

我要的是"文件系统"这种能力，谁提供由运行环境定：

Local FS
Remote FS
Container FS
…# 工具不需要知道底层是哪种
类比（电源插座）：插座统一的是"怎么插、插口什么形状"，但不规定插上去的是台灯还是电风扇——机制是 Harness 的，能力是插件的。
07 · 为什么不只是"多加几个 Tool"

一个在工具圈里做加法，一个把 Runtime 也开放

普通 Tool Framework

registerTool(...)
registerTool(...)
registerTool(...)

# 但核心 Loop 仍然固定：
while not done:
    call_model()

        execute_tool()

DSH

插件不仅能注册 Tool，还能参与调用前检查、执行、结果处理以及 Agent Loop 的后续控制——开放的不只是 Tool 本身，还包括 Tool 所在的 Runtime。官方扩展指南（Extension Cookbook）的扩展点：

工具注册pre-execute 拦截单调防护执行包装器后置处理UI 渲染会话事件follow-up / steer
一句话记忆：这些扩展点覆盖 Tool 执行前后、Session 渲染和 Agent 控制流程，全部通过明确的 Runtime 契约接入——不要求扩展者改写默认 Loop。
08 · Developer Preview

骨架放心依赖，细节别当契约

官方 README 仍把项目标记为 Developer Preview。原书以 2026-08-24 为技术冻结日，并把"版本敏感事实"与"架构解释"分开标注——这也是读这本书的方法。

相对稳定 · 架构语义

  • Harness 的职责、插件组合
  • Context / Service / Effect
  • Agent Loop、Tool Pipeline、Session Event
  • Capability / Provider
  • Sandbox / Approval / Lifecycle 的边界

容易变化 · 具体实现

  • CLI 参数、package 名称
  • Preset 目录、UI、事件名
  • Code Mode API
  • Subagent backend
  • Extension API
判断标准：越靠近"组织方式"越稳定，越靠近"具体实现"越易变。放心学它的架构思想，用时再查具体 API。
09 · 全书学习路径

先跑起来，再拆开看，最后自己动手

第一步先跑起来把 DSH 跑起来，建立直观感受

第三步亲手加一个能力从 Skill、Tool 或 Hook 开始
第四步理解 Everything is a Plugin插件体系

Task1（导读 + 第 1 章）解决的是"看懂"；这 8 步是"动手"路线，从第一步开始。主线：上手 → 组合 → 原理 → 运行时 → 设计。每章回答 4 个问题：解决什么工程问题 / 官方实现把它放在哪里 / 运行时为什么这样工作 / 怎样通过实验核对，而不是只接受概念。
