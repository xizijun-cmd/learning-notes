"一切皆插件"最后还差一句：

Creative 让 Agent 能改自己的底盘；Cordis Kernel 负责让"随便换"不至于散架。

核心一句话：Creative 把 Runtime 的组合结构变成了 Agent 可以观察、修改的对象；而真正托住这一切的，是一层只管规则、不管功能的 Cordis Kernel。

01 · 谁在说，谁在做

先把地基打回 Task1

模型只会生成 Token——它能"说"，不能"做"。中间必须有 Harness 把"说"接成"做"。

你 PTC 见过的那一幕：模型输出"我要调用 write"，没有 Harness 真的去执行，这句话就停在屏幕上，什么也不会发生。
这不是死循环——死循环是 Harness 在、但"喊停"坏了。这里是压根没人干活。
一句话记忆：模型出主意，Harness 跑腿。
02 · 把 Harness 拆两半

仓库只有一份，领料单各组不同

Harness 分两层：Host Plane（共享地基）和 Agent Plane（每会话自己的装配）。

仓库与领料单：
Tool Registry（工具注册表） = 公司仓库：所有货都在里面，只有一份。
给模型的工具清单 = 每个项目组的领料单：要哪些、以什么形式领，各组不同。
共享（Host）各自（Agent）
模型路由 Model Route提示词 Prompt（Task2 四套内容就不同）
工具注册表 Tool Registry给模型看哪些工具的清单
持久化 Persistence、沙箱 Sandbox上下文、会话状态
一句话记忆：Host 管"怎么有"，Agent 管"怎么用"。
03 · 四种装法

4 套 Preset = 同一套零件的 4 种装法

Preset 不是 Agent，是配置单。Task2 你亲眼看到的差异，全是 Agent Plane 的组合差异：

Preset定位相对 Standard 改了什么Task2 证据
Standard完整基线——bash + write 直接可用
PTC换 Tool Presentation能力不变，交互换成代码（TS 编排）直接调 write 报 UNKNOWN_TOOL
Minimal压到最薄只留固定 Prompt + 持久 Bash + str_replace_editor没有 write，用 echo 重定向
Creative加 Runtime 自引用加检查、挂载/卸载、Preset 编写指导上下文多出 Skills 声明
一个关键区分：Minimal 的 write 是没进清单（能力没暴露）；PTC 的 write 是换了入口（能力在，得走 run_code）。前者是"不存在"，后者是"存在但换了用法"——判断依据永远是 Trace，不是模型自述。
一句话记忆：一套零件表，四种装法——角色、提示词、呈现、上下文，全都是可组合的。
04 · Creative：能改自己的底盘

从"用能力"到"改能力来源"

Creative 的"创造"不是写作更有创意。它的目录叫 cordis/，核心是一个动作：cordis_mount——执行模型写的 TypeScript，在运行中的 Runtime 里挂载 / 卸载插件。

Agent→ 检查 Runtime→ 生成临时 Plugin→ Mount→ 获得新能力→ 使用 / 验证→ Unmount

这意味着 Agent 不只操作文件和网络，还能操作承载自己的那套组合。"运行一个 Agent"和"设计一个 Agent"的边界因此模糊了。

但有条线不能跨

官方把自修改定义为"信任边界（trust boundary）"，不是"安全沙箱"。
能改，不代表改完安全、正确、可恢复——这些要靠外面的工程机制兜：权限控制、人工审查、版本管理、测试、恢复。
所以别说成"安全的自我进化"。它是高信任能力，不是"不会翻车"。
一句话记忆：能改自己那份，改不到隔壁，也改不到仓库；正因为改的是自己，出问题没有上一层兜底。
05 · Cordis Kernel：不散架的规则

"一切皆插件"还差最后一块

如果什么都是插件，那"插件怎么组合"这件事本身谁管？这就是 Cordis Kernel 的存在理由——它只管四条规则，而且这四条不属于任何 Preset：

① 挂载与卸载

插件怎么进来、怎么出去

② 能力发现与依赖

谁依赖谁，按什么顺序起

③ 事件传递

插件之间怎么说话

④ 资源清理

退出时占着的东西怎么回收

为什么"挂载"本身不能是插件

挂载管的是"插件怎么组合"这件事本身。如果"管组合"的规则也能被组合掉，就没有任何稳定的东西来保证组合的正确性。

两个类比：裁判不能由参赛队自己换；量长度的尺子不能是随时会缩的。

微内核类比：哪里对，哪里不对

对不对
核心精简、功能外置的设计思路相通DSH 不是 OS 微内核——没有进程/内存/设备管理，只是 Agent Runtime 的插件体系
一句话记忆：插件是能换的零件，内核是换零件时"不散架"的规则——规则本身不能是零件。
06 · 自测

合上页面，先自己说一遍

用法：先口头回答，再点开对照。

Q1cordis_mount 做了什么？为什么说 Creative 让 Runtime 本身成为可操作对象？
它执行模型生成的 TypeScript，并在当前运行的 Runtime 里挂载 / 卸载插件。Agent 因此能在运行期间检查并调整承载自己的组合结构——从"使用能力"升级为"改造能力来源"，所以 Runtime 本身成了可操作对象。
Q2Cordis Kernel 负责哪些"不属于任何 Preset"的规则？
插件的挂载与卸载、能力的发现与依赖、事件的传递、资源退出时的清理。这些是稳定运行的基础语义，不属于 Standard / PTC / Minimal / Creative 任何一套。
Q3"DSH 就是微内核操作系统"，这个类比哪里对、哪里不对？
对：核心精简、功能外置的思路相通。不对：它不是 OS 微内核，没有进程/内存/设备管理那一层；它是 Agent Runtime 的插件体系。类比只能说明思路，不能当成同一类系统。
Q4Task2 观察到的 4 套 Preset 差异，现在能用 Task3/4 的概念解释了吗？
能。差异的本质是：同一个 Tool Registry（Host），四套 Preset 在 Agent Plane 的组合不同——Standard 完整装配、PTC 换 Tool Presentation、Minimal 裁剪 Prompt/Tools/Context、Creative 加 Runtime 自引用。不是 4 个 Agent 在跑。
07 · 速记 + 前三章串讲

合上书，记住这 7 条

  1. Creative 的"创造" = 改承载自己的 Runtime，不是写得更有创意
  2. cordis_mount：执行模型写的 TS → 挂载 / 卸载插件
  3. 自修改是信任边界，不是安全沙箱
  4. 4 套 Preset = 同一套零件表的 4 种装法（角色/提示词/呈现/上下文都可组合）
  5. Kernel 管 4 件事：挂载卸载、能力发现与依赖、事件传递、资源清理
  6. 微内核类比：思路对，系统类型不对
  7. 一切皆插件 ≠ 没有内核；规则本身不能是零件
前三章串成一条线：模型只会说（Task1）→ Harness 拆两半（Host 提供 / Agent 装配）→ Preset 是配置单（Task2/3 四种装法）→ Creative 能改自己那份 → Kernel 守住不散架的规则（Task4）。
