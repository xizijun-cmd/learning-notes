## 一、Creative：让 Runtime 成为可操作对象（3.6）

- 官方目录 `cordis/`，产品名"创造模式"。
- **"创造"不是写作更有创意**，而是：Agent 不仅能**使用** Runtime 提供的能力，还能在授权范围内**观察和修改 Runtime 本身**。
- 在 Standard 基础上增加的四类东西：
  1. 对 Runtime 的检查能力（能看到当前组合长什么样）
  2. Cordis 相关工具
  3. 插件实验能力
  4. 创建 / 修改 Preset 所需的指导

### cordis_mount 做了什么（图 3-7）

```
Agent
 → 检查当前 Runtime
 → 生成临时 Plugin（模型写 TypeScript）
 → Mount（挂载）
 → 当前 Session 获得新能力
 → 使用 / 验证
 → Unmount（卸载）
```

- 它能**执行模型生成的 TypeScript 代码**，并在当前运行的 Runtime 中挂载 / 卸载插件。
- 所以 Agent 不只是操作文件、脚本、网络——它能**改变承载自己的那套运行时组合**。

### Self-modification 的准确含义

- **不是**改模型参数或权重。
- **是**让 Runtime 的**组合结构**成为 Agent 可操作的对象。
- 副作用："运行一个 Agent"和"设计一个 Agent"的边界变模糊了。

### 风险边界（最容易漏的一点）

- 官方明确把自修改看作一条**信任边界（trust boundary）**，**不是安全沙箱**。
- 能力越强，越需要外层机制兜：权限控制、人工审查、版本管理、测试、恢复。
- 所以别把 Creative 说成"安全的自我进化机制"。准确说法：**它能改，但改得对不对、能不能恢复，取决于外面的工程机制。**

### 递归的准确含义（讨论后确认）

- 它能改的，是**承载自己的那份组合**（自己的 Scope 内）；
- 改不到隔壁的 Session，也改不到 Host 的仓库（Tool Registry）；
- 正因为改的是自己，出问题时**没有上一层兜底**——这就是"信任边界"的来源。

> 一句话记忆：Creative 给的是"改自己底盘"的能力，不是"改了不会翻车"的保证。

## 二、4 套 Preset 如何体现"一切皆插件"（3.7）

- 关键判断：一个 Agent 的最终表现，**不是由某个固定 Agent 类型单独决定**，而是三样东西共同形成：
  1. Host 提供的共享能力
  2. 当前 Runtime 的基础组合
  3. 当前会话通过 Preset 挂载的能力

| Preset | 一句话定位 | 相对 Standard 改了什么 |
|---|---|---|
| **Standard** | 完整 Agent composition | 基线：文件编辑、Shell、检索、Skills、Planning、Subagent、Workflow，按需装配 |
| **PTC** | Standard + 换 Tool Presentation | 能力不变，把"模型 ↔ 工具"的交互换成代码（TS 编排多步） |
| **Minimal** | 大幅裁剪 Prompt / Tools / Context | 只留精简 Persona/Context、常驻 Bash、str_replace_editor |
| **Creative** | Standard + Runtime 自引用 | 加 runtime inspection、model-written mount/unmount、Preset 编写指导 |

- **"插件化"不只针对 Tool**：Agent 的角色设定、提示词、工具呈现方式、上下文策略、部分 Runtime 能力，全都是可组合的部分。

> 一句话记忆：4 套 Preset 不是 4 个 Agent，是同一套零件表的 4 种装法。

## 三、"一切皆插件"不等于没有内核（3.8）

**Cordis Kernel 负责 4 类规则**（都不属于任何具体 Preset）：

1. 插件如何**挂载和卸载**
2. 能力如何**被发现和依赖**
3. **事件**如何传递
4. 资源在插件退出时如何**清理**

为什么必须有它：这些是 Runtime 的**基础语义**。只有它们稳定，插件才能被组合、替换、启停、销毁，而**不会让整个系统失去一致性**。

更准确的理解：**让 Kernel 只保留稳定的运行机制，把具体 Agent 能力交给插件和 Preset 去组合。**

### 为什么"挂载"本身不能是插件（讨论补充）

| 职责 | 一旦不稳定会怎样 |
|---|---|
| 挂载 = "谁能进来"的唯一入口 | 写错的插件混进来，该进的进不来 |
| 挂载还管**依赖顺序** | A 依赖 B，B 没到 A 就先挂上 → 拿到空壳（Task3 的 PENDING 就是这套机制在等） |
| 卸载负责**资源清理** | 文件句柄、进程、连接没人回收 → 泄漏，跑久了拖死 |
| 事件传递 | 顺序乱 / 丢失 → 插件之间协作断裂 |

**本质是悖论**：挂载管的是"插件怎么组合"这件事本身；如果"管组合"的规则也能被组合掉，就没有任何稳定的东西来保证组合的正确性。

> 两个类比：**裁判不能由参赛队自己换**；**量长度的尺子不能是随时会缩的。**

> 一句话记忆：插件是能换的零件，内核是换零件时"不散架"的规则——**规则本身不能是零件**。

### 微内核类比：哪里对，哪里不对

| | 说法 |
|---|---|
| **对** | 设计思路相似：核心尽量精简，功能放到外围组件 |
| **不对** | DSH/Cordis **不是**传统操作系统意义上的微内核；它没有 OS 那套进程/内存/设备管理，只是 Agent Runtime 的插件体系 |

> 一句话记忆：插件是"能换的零件"，内核是"换零件时不会散架的规则"。

## 四、本章小结（3.9 原文 5 条）

1. **Preset 决定当前 Session 组合哪些 Agent 能力**——不是每个 Session 复制一整套插件和底层设施，Agent 在自己的作用域里挂载需要的部分。
2. **Host Plane 负责共享与治理基础设施**，Agent Plane 决定当前 Session 如何组合、配置、向模型呈现。
3. **PTC 与 Standard 的差异在工具的呈现和调用方式**——底层 Tool Registry 不变，模型通过 Code Mode 用同一套能力。
4. **Minimal 通过减少提示词、运行时上下文、可见工具，把 Harness 压薄**——它是观察"Model + 极简 Harness"的基础环境。
5. **Creative 把 Runtime 组合结构变成 Agent 可观察、可修改的对象**——可扩展性提高，信任边界同时扩大，需要更严格的权限、审查、恢复机制。

## 官方自测 4 问

**Q1：cordis_mount 做了什么？为什么说 Creative 让 Runtime 本身成为可操作对象？**

- 它执行模型生成的 TypeScript 代码，并在当前运行的 Runtime 中挂载 / 卸载插件。Agent 因此能在运行期间检查并调整承载自己的组合结构——从"使用能力"升级为"改造能力来源"，所以 Runtime 本身变成了可操作对象。

**Q2：Cordis Kernel 负责哪些"不属于任何 Preset"的规则？**

- 插件的挂载与卸载、能力的发现与依赖、事件的传递、资源退出时的清理。这些是稳定运行的基础语义，不属于 Standard / PTC / Minimal / Creative 任何一套。

**Q3：有人说"DSH 就是微内核操作系统"，这个类比哪里对、哪里不对？**

- 对：核心精简、功能外置的设计思路相通。
- 不对：它不是 OS 微内核，没有进程/内存/设备管理那一层；它是 Agent Runtime 的插件体系。类比只能说明思路，不能当成同一类系统。

**Q4：回顾全程：Task2 观察到的 4 套 Preset 差异，现在能用 Task3/4 的概念解释了吗？**

- 能。Task2 看到的"能力清单不同、PTC 报 UNKNOWN_TOOL、轮次差异"，本质是：**同一个 Tool Registry（Host）**，四套 Preset 在 **Agent Plane 组合**上不同——Standard 完整装配、PTC 换 Tool Presentation、Minimal 裁剪 Prompt/Tools/Context、Creative 加 Runtime 自引用。不是 4 个 Agent 在跑。

## 我的理解检验（五站问答记录 · 2026-10-25）

> 保留当时的原话和纠正过程——错在哪，比答案本身更值得复习。

**第 1 站 · 谁在说，谁在做**

- 问：那句"我要调用 write"谁产出的？真正写文件的是谁？没有中间层会怎样？
- 答：模型产出；真正执行是 **Host**；没有中间层"可能会死循环"。
- 纠正：不是死循环，是**什么都不会发生**——句子停在屏幕上，模型接着编下一句（甚至编出"文件已创建"的假结果）。死循环是 Harness 的"喊停"功能坏了，是另一回事。
- 追问：PTC 的 write 是"不存在"还是"存在但换了用法"？
- 答：**存在但换了用法，依据是 Trace 里的呈现** ✅

**第 2 站 · 把 Harness 拆两半**

- 问：4 个 Session 共享什么、各自什么？
- 答：共享模型、共享系统资源、上下文各自独立 ✅；"共享系统提示词" ❌
- 纠正：**提示词属于 Agent Plane，各自一份**。反证：Task2 里四套 Preset 的上下文内容根本不同（Creative 多了 Skills 声明）。
- 追问：Tool Registry 与"给模型的工具清单"，哪个共享？
- 答：**前者共享、后者各自** ✅

**第 3 站 · 四种装法**

- 问：Minimal 为什么连 write 都没有，但沙箱还在？
- 答：**沙箱是共享的；write 只是没进 Minimal 的清单** ✅
- 结论：模型看不见 ≠ 底层不干活。

**第 4 站 · Creative 的递归**

- 问：新挂的工具进仓库还是进自己的单子？能改提示词吗？隔壁会受影响吗？
- 答：进自己作用域 / 能改 / 不会影响隔壁 ✅
- 结论：**能改的只有"承载自己的那份组合"，改不到隔壁，也改不到仓库。**

**第 5 站 · 内核为什么不能被插件化**

- 问："挂载"是谁提供的？如果它也能被替换，会怎样？
- 答：Harness（精确说是 **Cordis Kernel**）；替换会让 Preset 无法发挥、甚至打架，"具体原因不清楚"。
- 补全的四条原因（见第三节末）：入口唯一性、依赖顺序、资源清理、事件传递。本质是悖论：**管组合的规则，不能自己也被组合掉。**
