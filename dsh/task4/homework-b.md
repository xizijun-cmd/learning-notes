# 我理解的"一切皆插件"

一开始我以为"一切皆插件"就是"东西想换就换"。后来在 Task2 里开了 4 个 Session，分别选 Standard、PTC、Minimal、Creative，同一台机器只启动了一次 DSH——我才明白这句话真正的意思：不是东西随便换，而是每项能力都有明确的归属。共享的放 Host，会话的放 Agent Scope；Preset 只是张配置单。

它解决的工程问题，是 Agent 的组成越来越杂：工具、提示词、工具呈现方式、上下文策略，甚至部分运行时能力都在变。写死在核心程序里，改一处就要动全身；不同场景——有的要稳、有的要快、有的要自由——还得各维护一套。DSH 的办法是把"能力"和"组装方式"分开。我在 Task2 亲眼看到的：一台机器，一次启动，四个 Session 各挂一张配置单，跑出四种形态。模型、注册表、存储是共享的一份；提示词、给模型看哪些工具、上下文，是各自的一份。

但"一切皆插件"不等于没有内核。还有一层 Cordis Kernel，只管四条规则：插件怎么挂载和卸载、能力怎么被发现和依赖、事件怎么传递、资源退出时怎么清理。这四条不属于任何一套 Preset——它们是"换零件不散架"的保证。没有它们，插件组合起来会互相踩，替换会漏资源。所以准确的说法是：内核只管规则，插件才管功能。这和微内核的设计思路相通，但 DSH 不是操作系统意义上的微内核，只是借了思路。

它和"多注册几个 Tool"的区别，本质在开放的范围。多加几个 Tool，只是在工具圈里做加法，核心 Loop 不动；"一切皆插件"把工具周围的机制也交了出来：工具以什么方式呈现给模型、调用前怎么拦截、结果怎么处理、Loop 怎么控制。我的证据是 Task2 的 PTC：write 明明存在（在 run_code 里能调），直接调却报 UNKNOWN_TOOL——不是工具没了，是呈现方式换了。这事靠"加几个 Tool"做不到。

所以"一切皆插件"的"一切"，不是数量多，是连组织方式本身都可配置。而内核的存在，正是让这种自由不至于变成混乱。
