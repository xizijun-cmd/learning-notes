01 · 环境与 Workspace对应书中 2.1 / 2.2

Workspace 是 Agent 的"现实世界"

02 · 模型接入对应书中 2.3

模型不是 DSH 本体，是可替换的一项能力

DSH 是 Harness（运行框架），模型是通过 Provider / Model Adapter 挂进来的一项能力——今天挂 MiniMax，明天换 DeepSeek，Harness 不用动。这正呼应 Task1 的"一切皆插件：我要的是'模型'这种能力，不关心由谁实现"。

本次接入

MiniMax 2.7 highspeed（云端 API），设置 → 模型 → 添加自定义提供方。

书中演示

vllm 本地部署 Qwen + openai-responses 协议。本地跑不动大模型就换云端 API，协议必须与服务商实际实现一致。

03 · 实验 1 · 能力对照对应书中 2.4 / 表 2-1

4 套 Preset：同一个 Harness，四种"打开方式"

方法：4 个 Session 分别选 4 套 Preset，问"你当前可以使用哪些能力"。注意：下面写的是 Trace 自述，可不可信要看第 5 节的交叉验证。点标签切换：

bashreadwriteeditglobgrep
上下文：系统提示 + runtime-context（workspace-write 沙箱策略）。工具直接可调用——这是"标准打开方式"。
run_code（bash / read / write / edit 藏在 run_code 内部）
自述原话：工具"通过 run_code 调用"。同一套能力，换了个代码式的门面——PTC = Standard + Code Mode 工具呈现（官方目录 code/）。
bash文件操作（自述笼统：读取 / 编辑 / 创建）
清单最短、描述最笼统。自述说"能创建文件"——真的吗？看下面第 5 节的交叉验证。
bashreadwriteeditglobgrepweb_searchweb_fetchSkill: agent-experience
上下文多出 <system-reminder> 声明可用 Skills。独有网络搜索能力——四套里能力最多的一套。
一句话：差异不在"有没有能力"，而在暴露哪些、以什么方式呈现。

三个设计边界（2.4.2）

① 存在 ≠ 呈现

PTC 没删工具，只改了 model-facing presentation（摆在模型面前的样子）：write 从"货架上"挪进了 run_code 这个"柜子"。

② Preset ≠ System Prompt

Prompt 只是 Preset 五个格子（Persona / Prompt / Tools / Service / Runtime 行为）之一。在 Prompt 里写"你可以联网"，没挂 web_search 就是空口白话。

③ Host 共享 · Session 独立

1 栋楼 + 4 个房间：Web UI、模型配置、工具注册表共享；每个 Session 的子目录和对话记录各自独立。机制共享，内容独立。

04 · 实验 2 · 执行轨迹差分对应书中 2.4.3 / 表 2-2

同一道题，四种解法

任务：读目录 → 建 3 个文本文件 → 统计总行数 → 摘要。任务没规定文件内容，所以各模式行数不同很正常——比的是轨迹和方式，不是数值。

工具调用轨迹（每个色块 = 一次调用）

PTC4 轮 · 12+ 次调用 · 11 行

05 · 自述 vs 实际交叉验证 · 自测问题 1 的活证据

Minimal 的"自述"不可信

它说的（自述）

"我当前可以使用以下能力：1. 文件操作——读取文件、编辑文件、创建文件；2. Bash 命令执行……"

听起来挺全，对吧？

它做的（Trace）

实验 2 建文件用的是 echo -e "…" > file1.txt——它根本没有 write 工具，是用 shell 重定向硬凑的。

自述含糊地说"创建文件"，实际能力打了折。
为什么自述会错：模型的工具是 Harness 装配的，它自己并不知道被配了哪些——自述 = 猜，会漏报、多报、模糊合并。所以证据只能看 Trace 的客观调用记录。
06 · Benchmark 为什么选 Minimal对应书中 2.5

纯模型强 ≠ 放进任何 Runtime 都强

同一个引擎，装进跑车和卡车，成绩不一样。Agent 的表现 = f(模型, Harness, 工具, 上下文, 策略, 环境)——模型只是六个变量之一。本次实验同一个 MiniMax，塞进 4 套 Preset 行为就完全不同，就是活证据。

Model Benchmark

只测纯模型（答题、推理分）。变量只有模型一个。

Agent Benchmark

测"模型 + Runtime"整体。官方选 Minimal：砍掉 Harness 的花样，结果才逼近"测模型本身"。

三个容易踩的反向判断（原文 2.5）：
① 同一模型在 Standard 下表现更好，可能是 Harness 的功劳，别归给模型；
② 复杂 Harness 导致性能下降（多余 Tool Call、更长执行链），也别怪模型——我的 PTC 实验 4 轮、12+ 次调用就是例子；
③ 所以研究 Agent 除问"什么模型"，还要问"什么 Harness、什么工具 / 上下文 / 策略"。
一句话：Benchmark 里 Harness 越"隐形"，越知道模型几斤几两；Harness 越强，越分不清功劳是谁的。
07 · 自测

合上答案，先自己说一遍

用法：先别看答案，口头回答，再点开对照。说不顺的那题，回去看对应小节。

Q1为什么"模型对自身能力的说明"不能当证据？应该看什么？
模型的工具是 Harness 装配的，它不知道被配了哪些，自述 = 猜（漏报 / 多报 / 模糊合并）。例：Minimal 自称"能创建文件"，实际没有 write、用 echo > 重定向。应该看 Trace 的客观调用记录。
Q2Preset 改变的是"能力是否存在"还是"能力如何呈现"？两者是几件事？
两件事：存在 = 能力在不在；呈现 = 怎么暴露、以什么接口用。Preset 改的是呈现。例：PTC 的 write 存在（run_code 里能调），直接调却报 UNKNOWN_TOOL——存在没变，呈现变了。
Q3纯模型 Benchmark 很强，放进任何 Agent Runtime 都会同样强吗？
不一定。表现 = f(模型, Harness, 工具, 上下文, 策略, 环境)，模型只是变量之一。同一个 MiniMax 塞进 4 套 Preset 行为就不同。这正是 Agent Benchmark 存在、且官方选 Minimal 的原因。
08 · 速记清单

合上书，记住这 8 条

  1. 环境：Node ≥ 22.19 → npx 一条命令 → 127.0.0.1:3080
  2. Workspace = Agent 的"现实世界"，只在空目录实验
  3. 模型是 Runtime 可替换的一项能力，不是 DSH 本体
  4. Preset 改"能力如何呈现"，不改"能力是否存在"（两件事）
  5. PTC = Standard + Code Mode 工具呈现（官方目录 code/）
  6. Minimal 自述"能创建文件"实际没有 write——取证只看 Trace
  7. PTC 的 write 存在但直接调报 UNKNOWN_TOOL——存在 ≠ 呈现的铁证
  8. Model Benchmark ≠ Agent Benchmark，选 Minimal 是减少 Harness 变量
