DeepSeek Harness 技术入门 · 第 3 章

为什么 4 套 Preset，
不是 4 个 Agent？

这一章只回答这一个问题。答案你其实已经见过——只是没被点破。

核心一句话：共享的放 Host Plane，各会话的放 Agent Scope，Preset 只是一张配置单。
"一切皆插件"不是"东西随便换"，而是每项能力都有明确的归属。
01 · 先破一个误解

4 套 Preset ≠ 4 个 Agent

第一次读这章，很容易以为：既然 4 套 Preset 能力不同，那应该是 4 个 Agent、4 套代码、4 个循环。书里明确否定了这个理解。

想想你 Task2 干过的事：你在浏览器里开了 4 个 Session，分别选 Standard / PTC / Minimal / Creative。
你启动了几次 DSH？一次。模型配置是同一份，工具注册表是同一份，存储也是同一份。
你只是给每个 Session 挂了一张不同的配置单。

书里原文说：Host 里保留一套共享的常驻组合（模型、注册机制、持久化），某个 Session 进入自己的 Agent 作用域后，再挂载对应 Preset 提供的工具、提示词和会话级能力。

换句话说，Preset 定义的不是"一个 Agent 是谁"，而是"这个会话要挂哪些能力"。

一句话记忆：一个进程，一套地基；三间房，三种装修。Preset 是装修单，不是房子。
02 · 那两层到底怎么分

Host 管"怎么有"，Agent 管"怎么用"

先给一个类比，别急着记术语。

一栋写字楼。
Host Plane = 大楼的水电、电梯、门禁、财务、IT 机房。全楼共用，不用每家公司自己建一套。
Agent Plane = 每家公司自己的内部规矩：岗位怎么设、流程怎么走、员工能进哪些房间。
Host Plane（宿主层）Agent Plane（会话层）
回答什么系统怎么提供、统一管理能力当前会话怎么选择、组合、呈现能力
有什么Tool Registry、Persistence、Model Route、Sandbox、Subagent RegistryPersona、Prompt、Tool 暴露与呈现、Agent 本地服务

关键：一个 Tool 要拆成两半看

这是最容易搞混的地方。别问"这个工具属于哪一层"，要问"这件事属于哪一层"：

拿 write 来说：
"真正把内容写进磁盘"——Host 的事（filesystem service + policy）。
"模型能不能看见 write、它叫什么名字、参数怎么填"——Agent 的事。

所以书里反复强调：这是分工原则，不是绝对物理边界。不是去代码里找"这个工具在哪个文件夹"，而是看"这件事由谁负责"。

一句话记忆：Host 管"怎么有"，Agent 管"怎么用"。
03 · 为什么非要分层

不分层，会掉进两个坑

假设不做这个分层，只有两条路可走，两条都疼。

坑一：全放全局

就像办公室里只有一张公共桌子，谁放东西都影响别人。

Session A 加了个 Tool，Session B 突然也能看见——轻则干扰，重则同名撞车。

坑二：每个都起一套

就像 4 个人各买一台打印机、各拉一条网线。

模型路由、持久化、沙箱、子 Agent 注册中心全部重复建——贵，而且没法统一管理。

DSH 选的是中间路线：Host 持有一份"全进程唯一"的能力，各 Agent Scope 挂自己那份 Preset 贡献。该共享的共享，该各自的各自。

一句话记忆：共享的共享，各自的各自——这不是折中，是唯一能同时保住"隔离"和"省成本"的办法。
04 · 作用域：动态组合的边界

一项能力，必须先回答三个问题

Preset 能按会话动态挂能力，但能力不会自动变成全进程可见。每挂一项，都得问清楚：

① 属于谁？

只服务当前会话，还是全进程共享？

② 谁能看见？

注册在当前作用域，就只对当前会话可见。

③ 跟谁一起销毁？

会话结束就回收，还是跟进程一样常驻？

用你自己答对的那道题验证

问：在 Standard 的 Session 里临时加一个 Skill，PTC 的 Session 会不会也有？
答：不会。因为它注册在 Standard 自己的 Agent Scope 里，PTC 的作用域看不见它。
补一句：但这个 Skill 真要干活时依赖的文件系统、Shell，仍然在 Host——注册在 Agent，执行靠 Host。

注册错了会怎样？把"只该当前会话用"的服务注册成全局，它就变成所有 Session 都能访问，还可能和别人的同名服务打架。

一句话记忆：能力不是天生全局可见——看它注册在哪个作用域。
05 · Standard 为什么是"基线"

不是数插件，是给每项能力标归属

Standard 是能力最全的一套（读写、命令、搜索、规划、子 Agent 都有），所以它适合当参照系。但看书时别数"有多少个插件"，要问每项能力三个问题：属于哪个作用域？由谁提供？向谁开放？

类别管什么归属
角色与提示词人设、行为方式、提示内容跟 Agent / Preset
面向模型的工具暴露哪些 Tool 给模型跟 Agent / Preset
会话级状态Plan / Goal / Workflow 的运行状态跟 Agent / Session
Host 能力适配项把 Host 已有能力接进当前会话Host 提供、Agent 消费

书里图 3-4 最有意思：模型看到的每一个工具，背后都站着一个 Host 的服务。比如模型看到 tool-fs，真正干活的是 Host 的 filesystem service + policy；看到 tool-bash，背后是 shell executor。

这解释了为什么很多自定义 Agent 越做越复杂：
一开始没把两类问题分开——"模型能看到什么"（Agent）和"底层谁执行"（Host）。
结果在错误的层上改东西，越改越乱。

所以设计自定义 Preset 的实用口诀是：先判断改哪一层，再决定改什么。

"这个会话不许写文件" → 改 Agent（调工具集）；"所有文件操作必须进远程容器" → 改 Host（换 FS 和沙箱 Provider）。

一句话记忆：先问改哪层，再问改什么。
06 · PTC：同一批工具，换了个用法

不是"多了个 run_code"，是换了个门面

先回忆你 Task2 的那个红色报错。

PTC 里直接调 write → UNKNOWN_TOOL。模型愣了两下，改口说"我得在 run_code 里调"，然后成功了。

write 被删了吗？没有。它只是从"摆在货架上"挪进了"柜子里"。

这就是书里说的 Tool Presentation（工具呈现方式）：系统里有哪些工具（Tool Registry，在 Host，没变）和工具以什么形式给模型（Presentation，在 Agent，可变）是两件事。

传统：Native Tool Calling

模型看到 JSON 格式的工具说明，一步一调：LLM → 工具 A → LLM → 工具 B → LLM……

PTC：Code Presentation

模型看到一套 TypeScript SDK，直接写一段程序：循环、判断、并行都写在代码里，交给 run_code 跑。

源码层面差异极小：code/agent.cordis.yml 基本沿用 Standard 的组合，只加了一句 mode: code。

但别误会：减少往返 ≠ 一定更快

书里特别提醒：减少 round trip 是设计目标，不是性能保证。取决于任务适不适合程序化编排、模型写代码的水平、工具返回的数据量。

你的 Task2 就是反例：PTC 跑了 4 轮、12+ 次调用，反而是四套里最重的——因为任务太简单，写代码的准备工作比直接调还贵。
一句话记忆：不换工具，只换用法。
07 · Minimal：不是弱版，是显微镜

它故意把自己做薄

看到 Minimal 只有固定 Prompt、持久 Bash、str_replace_editor，第一反应是"这是阉割版 Standard 吧"。书里说不是——它是故意做薄的。

为什么故意做薄？
因为要当"Model + 极简 Harness"的观察基线：把工具、上下文、运行策略都减到最少，才更容易看清模型本身干得怎么样。
这就是 Task2 里官方 Benchmark 选 Minimal 的原因。

但注意一个容易被忽略的点：模型看不见 ≠ 底层不干活。Minimal 里那个持久的终端会话，照样要受 Host 的沙箱策略和命令执行环境约束——安全边界一点没少。

一句话记忆：模型看见的少，底层的治理还在。
08 · 自测

合上页面，先自己说一遍

用法：先口头回答，再点开对照。说不顺的那题，回去看对应小节。

Q1DSH 的分层避免了哪两种极端？各自代价是什么？
坑一全放全局：会话互相干扰、同名冲突（污染与耦合）。坑二每个都起一套：模型路由/持久化/沙箱/注册中心重复建（贵、难管）。DSH 走中间：Host 持一份单例，Agent Scope 挂各自的 Preset。
Q2"会话 A 新增的 Tool 影响到会话 B"——问题出在哪一层？
出在 Scope：这个 Tool 本该注册在 A 的 Agent Scope 内，却被注册到了全局/共享范围。修法：在 Agent Plane 里把它注册回自己的作用域，跟 A 一起创建和销毁。
Q3PTC 与 Standard 在源码层面的差异有多小？改变的是什么？
极小：基本沿用 Standard 组合，只加 Tool Presentation（mode: code）和 Code Mode SDK。改变的是"模型看到和使用工具的方式"，Tool Registry 仍在 Host，能力没有重写。
09 · 速记

合上书，记住这 7 条

  1. 4 套 Preset ≠ 4 个 Agent：一个 Host + 各自的 Agent Scope
  2. Host 管"怎么有"，Agent 管"怎么用"——分工，不是物理边界
  3. 不分层两条路都疼：全放全局会串，各起一套太贵
  4. 作用域三问：属于谁 / 谁能看见 / 跟谁一起销毁
  5. 能力拥有 ≠ 使用方式：PTC 换呈现，不换工具
  6. 减少往返是目标，不是性能保证（你的 PTC 4 轮就是反例）
  7. Minimal 是观察基线：模型看见的少，底层治理还在
